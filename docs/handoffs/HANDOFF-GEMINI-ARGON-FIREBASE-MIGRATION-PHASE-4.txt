9. TRANSACTION AND DATA INTEGRITY DESIGN
======================================================================

Use Firestore Web SDK transaction APIs and the existing repository foundation. Avoid bespoke transaction abstractions if a compatible foundation already exists.

For every mutation, answer:
- What is the canonical actor?
- What is the operation ID?
- What is the payload fingerprint?
- What records are read before writes?
- What invariant must be true at commit time?
- What documents are written atomically?
- What event/audit row is appended?
- What stale-write/expected revision precondition exists?
- What happens on network retry?
- What happens if the operation marker exists with same payload?
- What happens if the operation marker exists with different payload?
- What response is returned after a replay?
- Can two simultaneous requests bypass the invariant?

Important Firestore transaction rules:
- Perform all transaction reads before the first transaction write.
- Do not perform external network calls inside transaction callbacks.
- Avoid generating different operation IDs or timestamps on transaction callback retries unless the operation design explicitly supports it.
- Build deterministic IDs from operation identity when appropriate.
- Ensure transaction callback is retry-safe.
- Keep writes under Firestore limits.
- Never assume a prior query guarantees uniqueness against concurrent transactions.
- Use a document read/update lock or deterministic transaction guard for uniqueness across records.
- For inventory stock and payment balances, base calculations on the transaction's latest read values.
- Use integer IDR amounts when consistent with ledger model; avoid floating-point money drift.
- Preserve Asia/Jakarta business-date behavior where financial dates and due dates require it.
- Preserve idempotency on network retries. Replaying the same key + same payload should return prior result; same key + different payload must fail.
- Keep event collections append-only.

Do not introduce Cloud Functions to work around Firestore transaction limits. The approved architecture has no Cloud Functions.
